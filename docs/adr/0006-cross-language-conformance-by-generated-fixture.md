# 6. Cross-language agreement is proved by a generated fixture

- **Status:** Accepted
- **Date:** 2026-09-08
- **Milestone:** 1

## Context

Two pieces of this system compute the same thing in two languages, and they must
agree exactly.

The Rewards Engine builds a Merkle tree in TypeScript
(`@ponswars/rewards-math`). `RewardsDistributor` verifies proofs against it in
Solidity. Four separate conventions have to match:

1. the leaf encoding — `abi.encode(distributionId, account, amount)`
2. the double hash that keeps leaves out of the internal-node domain
3. sorted-pair hashing
4. promotion of an odd node to the next level

Nothing in either codebase forces them to share any of these. Both sides can be
individually correct, individually well-tested, and still disagree — and the two
failure modes are severe and asymmetric:

- **Too strict.** The contract rejects valid proofs and an entire 24-hour
  distribution is unclaimable. Loud, but only after a root is published, and
  §17 makes a published root immutable.
- **Too loose.** The contract accepts a proof for an allocation that was never
  made, and SPY leaves the contract to someone not entitled to it. Silent.

Unit tests on each side cannot catch either. Each would pass against its own
conventions.

## Decision

A fixture generated by the **real** TypeScript builder, consumed by the **real**
contract.

`scripts/generate-merkle-fixture.mjs` builds a seven-entry distribution with
`buildMerkleTree` and writes root, total and every proof to
`contracts/test/fixtures/merkle.json`.
`contracts/test/MerkleConformance.t.sol` reads it, publishes the root, and
claims every entry against the deployed contract — asserting the claims settle
the published total exactly and leave the distributor empty.

Three properties make this worth the machinery:

- **It uses production code on both sides.** No re-implementation of the tree in
  Solidity, and no re-implementation of the verifier in TypeScript.
- **It cannot go stale.** `--check` regenerates the fixture and compares it to
  the committed file. A change to the leaf encoding or the pairing rule fails
  the verify gate rather than landing quietly.
- **It proves something.** Tests for a tampered amount and another account's
  proof confirm the verifier discriminates, so a passing conformance run is not
  vacuous.

Seven entries, not eight: an odd count exercises the promoted-node path at more
than one level, which a power-of-two tree never reaches.

## Alternatives considered

**`vm.ffi` to call Node from Solidity.** Removes the committed fixture, but
requires FFI enabled in CI, makes the test depend on a working Node install
inside the Foundry process, and turns a deterministic test into an
environment-dependent one.

**Reimplement the tree in Solidity and compare.** This is what
`contracts/test/MerkleHelper.sol` does for the contract's own unit tests, and it
is genuinely useful there. It does not prove cross-language agreement, because
the Solidity reimplementation would be written by whoever wrote the contract and
would share its assumptions.

**Trust the unit tests on both sides.** Rejected for the reason above: both sides
pass against their own conventions, which is exactly the situation that hides a
mismatch.

## Consequences

- Regenerating the fixture is a required step when the tree format changes, and
  the gate enforces it.
- The pattern generalises. Any second implementation of a locked rule — a Python
  audit tool reproducing the battle score, a Solidity check of an allocation —
  should be pinned the same way rather than trusted to agree.
- One more generated artefact in the repository. It is small, readable, and its
  header names the script that produces it.
